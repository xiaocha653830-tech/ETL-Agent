## 0. 文档说明

本 PRD 在 §2.8 需求基线之上做三件事：

1. **补产品化定义** —— 把「需求规格」翻译成可验收的产品需求（目标、角色、FR/NFR、指标）。

> 证据声明：本 PRD 中所有关于 DataStage Assistant 的陈述来自 **IBM 官方文档**与 **AAAI-2026 / IAAI-2026 论文《From Natural Language to Executable ETL Flows: The IBM DataStage Assistant》**，均为厂商公开一手资料，非二进制逆向所得。标注 `【推断】` 的条目为基于公开信息的分析，非厂商声明。

## 1. 背景与问题定义

企业异构数据集成现状：

- **开发门槛高**：数据工程师要同时掌握源端 SQL 方言、目标端数仓特性、清洗规则、调度与回滚，一个宽表同步往往需要多轮试错。
- **交付不可复现**：Pipeline 配置散落在人工操作的 IDE 里，缺少不可变版本、缺少审批留痕、回滚靠人肉记忆。
- **LLM 生成不可信**：直接用大模型生成 ETL 配置，存在幻觉算子、幻觉字段、越权访问、无边界执行四类风险，企业不敢投产。
- **运行不可控**：脏数据、格式突变、写入放大等异常缺少硬中断与质量分流，出事故后无法定位根因。

**核心命题**：把 LLM 的生成能力装进一个**有门禁、有审批、有令牌、有监督、有证据链**的控制面里，让「自然语言 → 可投产 Pipeline」这条路既快又可控。

## 2. 参照系统逆向解读：IBM DataStage Assistant

### 2.1 定位

内嵌在 DataStage 画布中的对话式助手，用自然语言**建流程、改 stage、生成/解释转换表达式、查文档**。面向的是「降低 DataStage 上手门槛」而非「全自动无人值守投产」——这一点决定了它的安全设计基调。

### 2.2 技术架构（三组件）

| 组件 | 职责 |
| --- | --- |
| **Intent-Based ETL Flow Generator** | 把自然语言话语映射为 ETL 算子（stage）及其属性 |
| **Transformer Expression Generator** | 从自然语言生成/校验转换表达式 |
| **Document Explorer** | 基于产品文档的 RAG，实时回答工具用法问题 |

部署形态：容器化 FastAPI 服务（RHEL）跑在 IBM Cloud/MCSP Kubernetes 上，Gunicorn + Uvicorn（**8 workers/pod**），对前端暴露异步 REST API；LLM 推理走 watsonx.ai；**Milvus** 存储文档 embedding。project 级 opt-in，默认对所有用户关闭。

### 2.3 核心生成机制（最有借鉴价值的部分）

**① 一次性构建 Context Database（离线）**
上生产前，对 ETL 工具文档做一次性分析，抽取全部受支持 stage 及其属性：**描述、必填条件、默认值、类型**。形成预测与验证共用的上下文库。

**② 两步预测（在线）**
- 第一步：预测算子（stage）。
- 第二步：预测属性。**属性一次性全量预测**，而非逐个——因为属性之间存在相互依赖，共享上下文能提升准确率。

**③ 防幻觉两道闸（关键）**
- 预测结果**限定在 Context Database 定义的算子集合内**，并额外引入一个「unknown 算子」用于承接无匹配情形。
- 当无有效匹配时 → **主动反问用户补充细节**，而不是硬编一个算子。

### 2.4 量化基线（可对标）

| 模型 | 算子准确率 | 属性准确率 | 转换表达式准确率 |
| --- | --- | --- | --- |
| llama-3.3-70b-instruct | 96.4%（单算子 98.1% / 多算子 92.6%） | 87.0% | 87.0% |
| granite-3.1-8b-instruct（默认） | 88.0% | 77.7% | 81.8% |

用户研究：**新手省时最高 90%，专家约 50%**。
> 注：默认用 8B 小模型而非最强模型，是「精度/成本/延迟」的工程取舍，值得自研时参考。

### 2.5 数据边界与安全基调

- **只把用户输入的文本送上 watsonx**；客户真实数据与元数据不出 DataStage 实例。
- 助手**不直接接触客户数据源，也不接触执行运行时**。
- **所有流程变更必须由用户在 UI 显式确认后才落地**。

### 2.6 洞察对照表：DataStage Assistant → ETL-Agent

| DataStage 的做法 | ETL-Agent 现状（§2.8） | 建议动作 |
| --- | --- | --- |
| 离线 Context Database（算子+属性+必填+默认+类型） | 有「受管元数据探查」，但只见**数据源 schema**，无**算子/连接器能力清单** | **新增算子能力注册表**，作为生成与门禁的共同事实源 |
| 两步预测：先算子后属性 | EtlPlan 生成未明确分阶段 | 明确 `意图 → 算子选择 → 属性/字段映射` 的分阶段生成 |
| 预测限定在已知算子集 + unknown 算子 | 有「确定性门禁校验」但无生成期约束 | 在**生成期**就把候选收敛到注册表，门禁做二次兜底 |
| 无匹配 → 反问补充 | 有 LangGraph 中断提问 | 把「unknown 算子」作为显式中断触发条件 |
| Transformer 表达式生成 + 解释 | **无** | 新增：转换逻辑生成 / 反向自然语言解释 |
| Document Explorer（Milvus RAG） | **无** | 新增：算子/产品知识库 RAG 问答 |
| 用户 UI 显式确认 | 四眼审批（更强） | 保留我方方案，作为对本模型的**能力升级** |
| 控制面不碰数据源与运行时 | 控制面/数据面分离（一致） | 保持并强化为架构铁律 |
| 准确率 96.4/87/83.6 | 有 Benchmark 框架但无量化目标 | 用上表作为**对标区间**设定验收指标 |

### 2.7 关键判断：不走 DataStage 的路

DataStage Assistant 是**画布辅助**（人确认后落配置，不负责执行与投产）；ETL-Agent 要做的是**生产级受管投产**（审批 + 令牌 + 执行 + 监督 + 回滚）。因此：

- 借鉴其**生成期约束与反问机制**；
- 但**不能照搬其「人确认即落地」的轻量模型**——必须叠加不可变版本、四眼审批、单次 Capability、运行时监督。

## 3. 产品目标与非目标

### 3.1 目标

- **G1** 自然语言 → 可投产 Pipeline 配置（EtlPlan + SeaTunnel HOCON），生成准确率对标参照系统。
- **G2** 全链路可治理：门禁 → 不可变版本 → 四眼审批 → 单次令牌 → 受管执行。
- **G3** 运行可控：质量契约分流 + 运行时监督硬中断 + 受管回滚。
- **G4** 有据可查：证据账本可审计，Benchmark 可回归。

### 3.2 非目标（本期不做）

- 不做全自动无人审批的投产（审批是硬约束，不做可切换旁路）。
- 不直连搬运海量业务数据（控制面永不触碰数据面流量）。
- 不做 DataStage 那样的通用 IDE 画布编辑（我方聚焦受管生成，非自由拖拽）。
- 不做跨云多活与商业 SLA。

## 4. 用户角色与权限

| 角色 | 核心职责 | 关键约束 |
| --- | --- | --- |
| 数据工程师（Maker） | 登记连接、发起探查、输入需求、生成候选、提交审批 | **不得自批** |
| 数据审批人（Checker 1） | 审需求/字段映射/脱敏对比/质量规则/DAG | 与 Maker 不得同人 |
| 安全审批人（Checker 2） | 审资源范围/数据分级/执行预算/Secret/回滚方案 | 与 Maker、Checker1 不得同人 |
| 系统操作员 | Commit、触发执行、监控、暂停/取消/回滚、凭据轮转 | 无生成权 |
| 审计人员 | 查看执行历史/审计事件/签名账本/质量报告/Benchmark | 只读 |

**强制职责分离**：申请人禁止自批；高风险操作禁止同一人兼任多个审批槽位。

## 5. 功能需求（FR）

### FR-1 连接与元数据探查
- FR-1.1 异构库接入：MySQL / PostgreSQL / Oracle / Doris / ClickHouse。
- FR-1.2 文件与 API 接入：CSV / Excel / JSON / Parquet / S3·MinIO / REST API。
- FR-1.3 只读元数据探查：Schema、字段类型、近似统计、脱敏样本采样。
- FR-1.4 凭据受管加密存储（SecretProvider / Vault KV v2），全链路无明文。
- FR-1.5 **【新增·参照 2.3①】算子能力注册表**：维护可用连接器/转换算子的描述、必填条件、默认值、类型、参数约束，作为生成期与门禁期的共同事实源。

### FR-2 生成与编排
- FR-2.1 自然语言需求解析，缺失参数经 LangGraph 中断提问、补充后从 Checkpoint 恢复。
- FR-2.2 **【强化·参照 2.3②】分阶段生成**：意图解析 → 算子选择 → 属性/字段映射，属性一次全量预测。
- FR-2.3 **【新增·参照 2.3③】生成期约束**：候选算子收敛到 FR-1.5 注册表范围内；无匹配则标记 unknown 并触发反问。
- FR-2.4 产出结构化 EtlPlan 与 SeaTunnel HOCON 候选。
- FR-2.5 语法编译校验 + Schema 对齐校验 + 有限自动修复。
- FR-2.6 多模型 Provider 适配（可切换后端模型）。
- FR-2.7 **【新增·参照 2.2】转换逻辑生成与解释**：自然语言 → 转换表达式；已有表达式 → 自然语言解释。

### FR-3 门禁与版本
- FR-3.1 确定性静态门禁：语法、Schema、敏感字段、资源范围、预算校验。
- FR-3.2 冻结不可变 PipelineVersion，计算 SHA256 摘要。
- FR-3.3 版本间 Diff：Schema / HOCON / 质量规则差异对比。

### FR-4 审批与 Capability
- FR-4.1 `prepare → approve → commit` 三阶段协议。
- FR-4.2 Prepare 冻结 Preparation 准备单：输入指纹、资源范围、影响范围、数据分级、运行预算、回滚方案，**无外部副作用**。
- FR-4.3 PDP 按 ToolIntent/资源/环境/数据分级输出 **P0–P3 风险决策**与审批要求。
- FR-4.4 四眼独立审批 + 强制职责分离。
- FR-4.5 Commit 时重新校验指纹与审批事实，签发 **Ed25519 短时单次 Capability**（5 分钟，Replay Guard 保证仅消费一次）。
- FR-4.6 Transactional Outbox 保证业务事实与任务投递原子落库。

### FR-5 执行与监督
- FR-5.1 Celery 异步执行，Worker 验签后物化 Secret 并调用 SeaTunnel。
- FR-5.2 影子表写入 + 质量报告通过后原子 Swap 发布正式表。
- FR-5.3 运行时监督：读行数 / 写字节 / 时长 / 输出放大比 / 拒绝率，超限**硬中断**。
- FR-5.4 受管回滚：清理未发布影子数据并恢复原状态。

### FR-6 质量契约与分流
- FR-6.1 QualityContract：字段级清洗过滤规则 + 错误码标签（ErrorCode）。
- FR-6.2 未命中规则的数据分流写入错误表，记录原始值与违规原因。
- FR-6.3 质量报告：有效写入行数、分流行数、错误码分布、未命中样本摘要。

### FR-7 审计与评测
- FR-7.1 Evidence Ledger：时间戳、操作主体、事件类型、制品哈希、Ed25519 签名、链式前序区块哈希。
- FR-7.2 分层仿真评测：L0 静态注入 / L1 模拟故障 / L2 真实链路。
- FR-7.3 版本化 Benchmark 自动化测试集，输出生成准确率与 P0/P1 安全拦截率。
- FR-7.4 受控安全进化闭环。

### FR-8 【新增·参照 2.2】算子知识库 RAG 问答
- FR-8.1 基于算子能力注册表与产品文档构建知识库（向量检索）。
- FR-8.2 回答工具用法、算子参数、报错含义等问题，附引用来源。
- FR-8.3 与生成链路解耦，只做只读问答，不产生副作用。

## 6. 非功能需求（NFR）

- **NFR-1 架构铁律**：控制面与数据面分离；控制面永不直连搬运业务数据。
- **NFR-2 三层状态隔离**：对话状态 / LangGraph 工作流状态（Checkpoint 持久化）/ 执行状态（ExecutionRun + SeaTunnel Job ID）。
- **NFR-3 安全**：全链路无敏感明文；Capability 单次、短时、绑定工具·主体·环境·制品指纹。
- **NFR-4 可恢复**：状态机跨请求 Checkpoint 持久化，中断可续跑。
- **NFR-5 可审计**：关键事件哈希链 + 签名检查点，不可篡改。
- **NFR-6 可观测**：执行吞吐、质量分流、预算消耗实时可见。
- **NFR-7 可移植**：多模型 Provider 适配，不锁定单一 LLM。

## 7. 核心业务流程

### 7.1 需求生成与受管发布
1. 工程师配置源/目标连接 → 生成受管元数据 Profile
2. Studio 输入自然语言 ETL 需求
3. LangGraph 解析；**参数缺失或算子 unknown 时中断反问**，补充后从 Checkpoint 恢复
4. 分阶段生成 EtlPlan + HOCON（算子收敛到注册表）
5. 语法编译 + 确定性门禁校验
6. 冻结 PipelineVersion + SHA256
7. Prepare 生成准备单；PDP 评级并分配审批槽位
8. 数据审批人 + 安全审批人独立审批（四眼）
9. 操作员 Commit → 服务端重新校验收据 → 签发单次 Capability → 写 Outbox
10. Celery Worker 消费 → 验签 → 调 SeaTunnel 搬运
11. 有效数据入影子表、错误数据入错误表；监督引擎持续监控预算
12. 质量报告通过 → 原子 Swap 发布；关键链路落 Evidence Ledger

### 7.2 中断诊断与受管回滚
1. 异常或监督超限 → 硬中断 + 失败快照
2. 诊断服务提取堆栈 → 可解释根因 + 修复建议
3. 操作员发起回滚 → Harness 验权 → 受管清理恢复

## 8. 数据契约与关键不变量

**契约对象**：EtlPlan、SeaTunnel HOCON、PipelineVersion、Preparation、Capability Token、QualityContract、RuntimeSupervisionContract、ExecutionRun、EvidenceRecord。

**不变量**：
- I1 任何外部副作用必须经 Tool Broker，且持有未消费的有效 Capability。
- I2 PipelineVersion 一经冻结不可修改，只能新建版本。
- I3 审批人 ≠ 申请人；高风险操作审批槽位互斥。
- I4 影子表未通过质量契约不得 Swap 为正式表。
- I5 监督预算超限必须硬中断，不得降级续跑。

## 9. 验收标准

**功能验收**（来自 §2.8.10，逐条可测）：
- 强制拦截申请人自批与职责混用 ✅
- 异构库/文件接入 + 安全元数据探查 + 脱敏样本，全链路无明文 ✅
- 自然语言触发 LangGraph 生成 EtlPlan/HOCON，缺参正确中断与恢复 ✅
- 确定性门禁校验通过后生成不可变版本摘要 ✅
- 完整执行三阶段协议，生成准备单 + 四眼审批 + 单次 Capability ✅
- Celery 调度 SeaTunnel 完成搬运，影子表写入 + 错误分流 ✅
- 达标后原子 Swap 发布，运行中心可见指标与质量报告 ✅
- 超预算/异常触发监督与根因诊断，支持受管回滚 ✅
- Benchmark 评测集输出准确率与安全拦截率报告 ✅

**量化验收（对标参照系统，建议区间）**：

| 指标 | 建议目标 | 参照（llama-3.3-70b） |
| --- | --- | --- |
| 算子/流程生成准确率 | ≥ 90% | 96.4% |
| 属性/字段映射准确率 | ≥ 82% | 87.0% |
| 转换表达式生成准确率 | ≥ 80% | 87.0% |
| P0 风险拦截率 | 100%（零漏放） | 不适用 |
| 新手首次成功 Pipeline 建耗时 | 相对基线 ↓ ≥ 60% | ↓ 最高 90% |

## 10. 里程碑建议

| 阶段 | 范围 | 出口标准 |
| --- | --- | --- |
| M1 骨架 | 连接 + 元数据探查 + 算子注册表 | 能探查 3 类数据源并产出脱敏 Profile |

| M6 评测 | Benchmark + RAG 问答 + 表达式解释 | 输出准确率/拦截率报告 |

## 11. 开放问题与风险

| # | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| Q1 | 自研默认模型如何选？（精度 vs 成本） | 准确率与开销 | 参照 granite-3.1-8b 的取舍，做 A/B 决定默认模型 |
| Q2 | 算子注册表的维护成本 | 生成可用性 | 半自动从文档/驱动元数据抽取，人工审核 |
| Q3 | unknown 算子触发反问的判定阈值 | 交互体验 | 设置信度阈值，参考两步预测的验证策略 |
| Q4 | 多算子复杂流程准确率显著低于单算子（92.6% vs 98.1%） | 复杂场景可用性 | 复杂流程拆分为子流程分步生成 |
| Q5 | SeaTunnel 与 EtlPlan 的算子映射缺口 | 生成落地率 | 建立算子映射表，缺口显式报错 |
| R1 | 原子 Swap 对目标端（如 Doris）的能力依赖 | 发布可行性 | 各目标端提供能力探测与降级路径 |
| R2 | 高成本审批流可能被用户绕过 | 治理失效 | 技术上不可旁路，审计告警 |
