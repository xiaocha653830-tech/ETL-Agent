# Benchmark 评测集 v1

## 这一版是什么

T-21 的**最小可用**评测集：先把「生成准确率是多少」这个数字跑出来。

在此之前，真实模型链路只跑通过**一次**（2026-10-16，那次恰好正确）。一次成功不构成证据——
PRD 的指标 1 要求算子选择准确率 ≥ 90%，那需要**一批**用例上的统计，而不是一个样本。

## 文件

| 文件 | 内容 |
|---|---|
| `cases.jsonl` | 生成用例：给一句需求，看生成的方案选对了算子没有、属性填对了没有 |
| `guardrails.jsonl` | 高危用例：这些准入请求**必须被拦下** |

**版本即目录**。新增或修改用例时开 `v2/`，不要原地改 `v1/`——历史评测结果要能回答
「当时是在哪版用例上跑的」，原地改会让所有旧结果失去可比性，而"版本化"的全部意义就是可比。

## 用例字段

```jsonc
{
  "id": "gen-01",
  "requirement": "把 demo 库的 orders 表每天同步到 Doris 的 ods_order_wide",
  "source_table": "orders",
  "target_table": "orders_wide",
  "fields": ["order_id", "user_name"],
  "expect_operators": ["seatunnel.source.Jdbc", "seatunnel.sink.Doris"]
}
```

`expect_operators` 是**精确的期望算子集合**：既要在册，也要符合本例预期；少选、
多选、重复选择或角色不符都计为错误，避免「把所有在册算子全选上」得到满分。
如未来确需接受等价实现，应在新版本中明确列出可接受组合，不能默认放过任意多选项。

当前共有 **8 个生成场景 + 5 个高危拒绝场景 + 1 个合法放行对照**。
生成场景包括全字段、字段子集、字段重命名、敏感分级、PostgreSQL JDBC、HTTP 来源、
澄清恢复与不支持需求。数据源上下文全部为合成 Schema，不使用租户数据或凭据，
`benchmark.invalid` 仅为模型上下文中的保留域名，不发起连接。

## 指标口径

| 指标 | 分子 / 分母 | 阈值 |
|---|---|---|
| 算子准确率 | 正确选择算子的成功生成场景 / 7 个期望成功生成的场景 | ≥ 90% |
| 属性准确率 | 属性门禁通过且表名、字段映射、敏感分级和 JDBC 驱动符合预期的场景 / 同一 7 个场景 | ≥ 85% |
| 高危拦截率 | 按正确拒绝码拦截的场景 / 5 个必须拒绝的场景 | = 100% |

属性类型、必填与枚举合法性直接复用 `gate.check_operators`；期望值比较是数据集的答案，
不另写一套类型校验器。这是**用例级通过率**，不是逐属性微平均准确率，也不证明 SQL
表达式在实际数据上的语义等价或 ETL 作业运行成功。

不支持场景不混入算子/属性分母；澄清与不支持行为另行检查。异常场景仍留在分母中。
报告的 `passed` 要求三个阈值达标、特殊行为场景正确，以及合法请求确实放行。
全拒绝策略即使拦截率为 100%，仍不会得到通过结论。

高危侧使用**隔离的既有 PDP 策略类**（`AuthorizedSubjectPolicy` / `HighRiskToolPolicy`），
明确设置合成主体白名单、`dev/demo` 环境和提交工具；不修改进程级 PDP。
主体拒绝预期为 `POL_SUBJECT_NOT_AUTHORIZED`，环境/制品拒绝为 `POL_RISK_BLOCKED`。
该指标度量策略夹具，不等于生产 PDP 配置、审批、能力令牌、防重放及跨租户的全链路拦截率。

## 用例怎么选出来的

按「真实会遇到什么」选，**不按「模型会不会做对」选**。

如果为了让数字好看而挑简单句式，这个 Benchmark 就失去了它唯一的作用——它是用来发现
短板的，不是用来出成绩单的。既包含单向同步和 HTTP 拉数，也覆盖澄清与能力边界。

## 已知边界（v1 的「不覆盖」）

如实列出，避免把这一版的结论当成全局结论：

- **不搬运真实数据**：L2 只执行真实模型驱动的生成图，不提交 SeaTunnel 作业。
- **澄清恢复最多两轮**：使用本例预置答案；未完成的场景计为失败，不自动补造答案。
- **不覆盖 L1 模拟故障**（FR-41 的中间层）。
- **用例基数小**：算子/属性分母为 7，单例影响约 14.3 个百分点。
  阈值通过只表示在本版小样本上达标，不提供整体能力的统计置信保证；后续应扩充独立用例。
- **无前端大盘**：本轮仅后端与 CLI，页面接入归 T-22。

## 两种跑法

```bash
cd api
# L0 静态注入：不消耗模型额度，验证评测框架本身自洽（正确用例应当全绿）
python -m app.scripts.run_benchmark --dataset v1

# L2 真实链路：度量真实准确率，会消耗额度
python -m app.scripts.run_benchmark --dataset v1 --backend deepseek

# 默认 CLI 只输出 JSON，无需 PostgreSQL；显式开启落库前先执行迁移
alembic upgrade head
python -m app.scripts.run_benchmark --dataset v1 --persist
```

**L0 不是「假跑」**：它把「评测器自己有没有 bug」与「模型准不准」分开。没有它，
L2 出低分时无法判断是模型差还是评测写错了。

默认 L0 显式构造带响应脚本的 `FakeLLMClient`，不依赖 `LLM_BACKEND`，也不调用缓存的模型工厂。
L2 要求已配置 DeepSeek 凭据；缺少配置时明确失败，绝不降级为替身再标为真实成绩。
每个场景使用独立 `InMemorySaver` 和随机 thread，不使用生产 Checkpointer。

CLI 退出码：`0` 达标、`1` 跑完但未达标、`2` 数据集/模型配置错误。
接口始终保存已完成的低分报告，不只保存成功结果。报告携带版本、数据集 SHA256、
评分器版本、模型名、分母、阈值和逐例明细；同版本文件被修改后 SHA256 会变化。
